# 05. 앱 개발 전략 & 로컬 개발 환경 가이드

> 웹+앱 동시 개발의 확정 전략과 로컬(Windows) 개발 환경 표준. 개발 산출물·명세서는 이 구조를 기준으로 작성한다.

## 1. 앱 전략 (확정: 단계적 하이브리드)

### 결정
- **1단계(P1~P2)**: Next.js 웹(PWA)을 본체로 개발하고, **Capacitor로 래핑**해 iOS/Android 스토어 출시. 코드베이스 1개.
- **2단계(전환 트리거 충족 시)**: **Expo(React Native)** 앱을 병행 개발. lib/core의 공용 로직을 패키지로 승격해 재사용하고 화면만 네이티브로 재구현.

### 근거
1. P1 성패 = SEO 콘텐츠 수요 확보 → SSR 웹이 본체일 수밖에 없음. 앱을 먼저 만들면 SEO 자산이 없다.
2. P1 앱 필수 네이티브 기능은 3개뿐 — 카메라(계약서 촬영 업로드), 푸시(일정 리마인더·D-day), 스토어 입점 — 전부 Capacitor 공식 플러그인으로 커버.
3. 팀 5~7명 규모에서 코드베이스 2개(웹+RN)를 처음부터 유지하는 비용 > 하이브리드 UX 열세 비용.
4. 사용자가 Expo 경험 보유 → 전환 시 러닝커브 없음. lib/core에 로직을 격리해두면 전환 비용 최소.

### Expo 전환 트리거 (하나라도 충족 시 검토 개시)
- AI 플래너 채팅의 UX 고도화 요구(음성 입력, 리치 인터랙션)가 웹뷰 성능 한계에 부딪힘
- 홈화면 위젯(D-day·일정), 백그라운드 동기화 등 웹뷰 불가 기능이 로드맵에 확정
- 앱 유입 비중 50% 초과 + 앱 리텐션이 웹 대비 유의미하게 낮음(웹뷰 체감 이슈 데이터 확인 시)
- P3 거래(전자계약·에스크로) 단계에서 생체인증 등 네이티브 보안 요구 발생

### 하이브리드 구현 원칙
- Capacitor는 **정적 자산 내장 + 원격 URL 혼합** 중 원격 URL 모드(Live URL) 기본: 배포 즉시 앱 반영, 심사 리스크는 코어 화면 정적 내장으로 완화. (스토어 정책상 결제·핵심 기능 변경은 심사 준수)
- 인앱 결제 회피 설계: 디지털 멤버십 결제는 스토어 정책 검토 필수(웹 결제 유도 링크아웃 정책 준수). 실물 서비스(예식·스드메) 예약 결제는 외부 PG 허용 대상.
- 푸시: FCM(Android)+APNs(iOS)를 Capacitor Push 플러그인으로. 알림 토픽: D-day 리마인더 / 일정 확정·변경 / 계약 단계 알림 / 케어 메시지.
- 카메라·파일: @capacitor/camera + 파일 피커. 촬영본은 업로드 전 클라이언트 리사이즈(≤20MB 규격 준수).
- 딥링크: 공유 리포트·초대(커플 연동)용 유니버설 링크/앱 링크 설정.
- WebView 성능 가드: 목록 가상화, 이미지 lazy, 애니메이션은 CSS transform 위주, Lighthouse 모바일 80+ 유지.

## 2. 폴더 구조 (표준 — 단일 Next.js 앱, saju 프로젝트 스타일)

> 모노레포(Turborepo) 대신 사용자 기존 프로젝트(saju)와 동일한 단일 앱 구조를 표준으로 확정. 로직 격리 원칙은 lib/core로 유지하여 Expo 전환 시 재사용성 보존. 실제 스캐폴드는 weddingclear_scaffold.zip으로 생성됨.

```
weddingclear/                     # 리포지토리 루트 (단일 Next.js 앱)
├─ .claude/                       # Claude Code 설정 (선택)
├─ app/                           # Next.js App Router
│  ├─ (marketing)/                # 랜딩·SEO 콘텐츠 (블로그/가이드)
│  ├─ (auth)/login, onboarding/   # 로그인·온보딩
│  ├─ (consumer)/                 # 소비자: planner(AI)·explore(탐색)·reports(검토)·budget·checkin
│  ├─ (vendor)/                   # 업체 어드민 (P2)
│  ├─ (admin)/                    # 운영자 콘솔
│  ├─ api/                        # Route Handlers: documents/reports/estimates/penalty/prices/payments/ai
│  ├─ layout.tsx / page.tsx / globals.css
├─ lib/
│  ├─ core/                       # ★도메인 로직 — React/Next import 금지 (Expo 재사용 대비)
│  │  ├─ rules/                   # 검출 룰 20종 (DetectRule)
│  │  ├─ pricing/                 # 위약금 룰 엔진(penalty.ts)·총액/다이내믹 계산
│  │  └─ schemas/                 # zod 스키마 (AI 출력 ReportSchema 등)
│  ├─ ai/                         # Claude 클라이언트·프롬프트·출력 검증 (서버 전용)
│  ├─ supabase/                   # client.ts(브라우저)/server.ts(서버) 초기화
│  └─ utils/
├─ types/                         # database.ts (supabase gen types 자동 생성)
├─ supabase/
│  ├─ migrations/                 # SQL 마이그레이션 (db diff로 생성, 단일 진실)
│  ├─ seed.sql                    # detect_rules·penalty_rules·추가금 사전 시드
│  └─ functions/                  # Edge Functions (파기 배치 등)
├─ docs/                          # 프로젝트 컨텍스트 문서 (00~05 사본)
├─ public/
├─ scripts/                       # Windows .bat + node 스크립트 (dev-setup.bat, 참가격 수집 등)
├─ _local_reports/                # 로컬 전용 산출물·샘플 (git 제외)
├─ tmp/                           # 임시 (git 제외)
├─ CLAUDE.md / AGENTS.md / README.md
├─ .env.example / .gitignore
├─ package.json / tsconfig.json / next.config.ts / tailwind.config.ts
├─ postcss.config.mjs / eslint.config.mjs / vercel.json
└─ (앱 착수 시) capacitor.config.ts + android/   # Capacitor는 같은 리포에 추가
```

### 구조 원칙
- **로직은 lib/core, 화면은 app**: AI 프롬프트·검증, 룰 엔진, 가격 계산은 lib/core에 격리(React/Next import 금지) — Expo 전환·테스트·재사용의 핵심. 전환 시 lib/core를 패키지로 승격.
- **DB 변경은 supabase/migrations로만**: 대시보드 수동 변경 금지, `npm run db:diff`로 마이그레이션 생성 후 커밋, `npm run db:types`로 타입 재생성.
- **환경 분리**: local(도커) → staging(Supabase 프로젝트 A + Vercel preview) → production(프로젝트 B). 키는 .env.local(.gitignore), 목록은 .env.example.
- **비밀·개인정보**: 서비스 롤 키·ANTHROPIC_API_KEY는 서버 전용. 클라이언트엔 anon key만. 업로드 원문·경로를 로그에 남기지 않는다. 계약서 샘플은 _local_reports/samples(git 제외).

## 3. 로컬 개발 환경 (Windows 기준)

### 필수 설치
| 도구 | 버전/비고 |
|---|---|
| Node.js | LTS(20+) — nvm-windows로 버전 고정 권장 |
| Git | + GitHub 리포 (main/dev 브랜치, PR 기반) |
| Docker Desktop | Supabase 로컬 스택 실행용 (WSL2 백엔드 활성화) |
| Supabase CLI | scoop 또는 npx로 설치. `supabase start`로 로컬 DB/Auth/Storage 기동 |
| Android Studio | Capacitor 안드로이드 빌드 (SDK+에뮬레이터). JDK 17 |
| (iOS) | 로컬 macOS 없으면 클라우드 CI(Codemagic/EAS 등)로 빌드·배포 |
| VS Code | 확장: ESLint, Prettier, Tailwind, Prisma/SQL 도구 |

### 최초 셋업 순서
```bat
:: 0) 스캐폴드 압축 해제 후 리포 초기화
cd weddingclear
git init && git add . && git commit -m "scaffold"

:: 1) 의존성
npm install

:: 2) 환경변수
copy .env.example .env.local
:: → supabase start 출력의 URL/anon key, ANTHROPIC_API_KEY, 토스 테스트 키 기입

:: 3) 로컬 Supabase 기동 + 마이그레이션·시드 + 타입 생성
npm run db:start
npm run db:reset
npm run db:types

:: 4) 웹 개발 서버
npm run dev            :: http://localhost:3000

:: (셋업 일괄 실행: scripts\dev-setup.bat)
```

### 일상 개발 플로우
1. dev 브랜치에서 기능 브랜치 생성 → 작업 → PR.
2. DB 변경: 로컬에서 스키마 수정 → `npm run db:diff -- -f <이름>` → 마이그레이션 커밋.
3. 타입 동기화: `npm run db:types` (types/database.ts 재생성).
4. 테스트: lib/core는 vitest 단위 테스트 필수(룰 엔진 경계값), E2E는 Playwright.
5. 배포: Vercel(웹, preview→production), 앱은 웹 배포 반영 + 네이티브 변경 시에만 스토어 제출.

### AI 개발 시 로컬 주의
- Claude API 호출은 서버(Route Handler) 경유만 — 클라이언트 직접 호출 금지(키 노출).
- 프롬프트·룰(prompt_fragment)은 lib/core/rules에 코드로 관리(버전 태깅), DB detect_rules와 시드로 동기화.
- 로컬 테스트용 계약서 샘플은 `_local_reports/samples/`(gitignore, 개인정보 마스킹본만 커밋 허용).

## 4. 개발 단계별 앱 마일스톤
| 시점 | 산출 |

| P1 M1 | 웹(PWA) 출시 — 홈화면 추가 배너, 오프라인 셸 |
