# 05. 앱 개발 전략 & 로컬 개발 환경 가이드

> 웹+앱 동시 개발의 확정 전략과 로컬(Windows) 개발 환경 표준. 개발 산출물·명세서는 이 구조를 기준으로 작성한다.
> **개발 순서는 `docs/07_개발명세서.md` §1.3의 8단계를 따른다**(v2.0, D-20). 이 문서의 단계 번호도 그 정의를 쓴다.

## 1. 앱 전략 (확정: 단계적 하이브리드)

### 결정
- **1단계**: Next.js 웹(PWA)을 본체로 개발하고, **Capacitor로 래핑**해 iOS/Android 스토어 출시. 코드베이스 1개.
- **2단계(전환 트리거 충족 시)**: **Expo(React Native)** 앱을 병행 개발. lib/core의 공용 로직을 패키지로 승격해 재사용하고 화면만 네이티브로 재구현.

### 근거
1. 검색 유입(SEO 콘텐츠)이 초기 수요 확보의 축이다 → SSR 웹이 본체일 수밖에 없다. 앱을 먼저 만들면 SEO 자산이 없다.
2. 앱에 필요한 네이티브 기능은 3개뿐 — 카메라(계약서 촬영 업로드), 푸시(일정 리마인더·D-day), 스토어 입점 — 전부 Capacitor 공식 플러그인으로 커버된다.
3. 팀 5~7명 규모에서 코드베이스 2개(웹+RN)를 처음부터 유지하는 비용 > 하이브리드 UX 열세 비용.
4. 사용자가 Expo 경험 보유 → 전환 시 러닝커브 없음. lib/core에 로직을 격리해두면 전환 비용 최소.

### Expo 전환 트리거 (하나라도 충족 시 검토 개시)
- AI 플래너 채팅의 UX 고도화 요구(음성 입력, 리치 인터랙션)가 웹뷰 성능 한계에 부딪힘
- 홈화면 위젯(D-day·일정), 백그라운드 동기화 등 웹뷰 불가 기능이 로드맵에 확정
- 앱 유입 비중 50% 초과 + 앱 리텐션이 웹 대비 유의미하게 낮음(웹뷰 체감 이슈 데이터 확인 시)
- **5단계 거래**(전자계약·3자 서명·분할 결제)에서 생체인증 등 네이티브 보안 요구 발생
- **4단계 연결**의 실시간 채팅(F-C-27)이 웹뷰 백그라운드 제약으로 알림 지연을 겪음

### 하이브리드 구현 원칙
- Capacitor는 **정적 자산 내장 + 원격 URL 혼합** 중 원격 URL 모드(Live URL) 기본: 배포 즉시 앱 반영, 심사 리스크는 코어 화면 정적 내장으로 완화. (스토어 정책상 결제·핵심 기능 변경은 심사 준수)
- 인앱 결제 회피 설계: 디지털 멤버십 결제는 스토어 정책 검토 필수(웹 결제 유도 링크아웃 정책 준수). 실물 서비스(예식·스드메) 예약 결제는 외부 PG 허용 대상.
- 푸시: FCM(Android)+APNs(iOS)를 Capacitor Push 플러그인으로. 알림 토픽: D-day 리마인더 / 일정 확정·변경 / 계약 단계 알림 / 케어 메시지.
- 카메라·파일: @capacitor/camera + 파일 피커. 촬영본은 업로드 전 클라이언트 리사이즈(≤20MB 규격 준수).
- 딥링크: 공유 리포트·초대(커플 연동)용 유니버설 링크/앱 링크 설정.
- WebView 성능 가드: 목록 가상화, 이미지 lazy, 애니메이션은 CSS transform 위주, Lighthouse 모바일 80+ 유지.

## 2. 폴더 구조 (표준 — 단일 Next.js 앱, saju 프로젝트 스타일)

> 모노레포(Turborepo) 대신 사용자 기존 프로젝트(saju)와 동일한 단일 앱 구조를 표준으로 확정. 로직 격리 원칙은 lib/core로 유지하여 Expo 전환 시 재사용성 보존.
>
> **리포지토리 폴더명은 `wstory` 이고 package name 은 `weddingclear` 다.** 아래 트리는 실제 리포 상태를 반영한다.

```
wstory/                           # 리포지토리 루트 (단일 Next.js 앱, package name: weddingclear)
├─ .claude/                       # Claude Code 설정 (선택)
├─ app/                           # Next.js App Router
│  ├─ (marketing)/                # 랜딩·SEO 콘텐츠 (블로그/가이드)
│  ├─ (auth)/login, onboarding/   # 로그인·온보딩
│  ├─ (consumer)/                 # 소비자: explore(탐색)·planner(AI)·reports(검토)·budget·checkin
│  ├─ (vendor)/                   # 업체 어드민
│  ├─ (admin)/                    # 운영자 콘솔

│  ├─ ui/                         # shadcn/ui 기본 + AssetImage·LoadingState·EmptyState·ErrorState
│  ├─ layout/                     # ConsumerShell·BottomTabNav·AdminShell

│  └─ utils.ts                    # cn() 등 공용 유틸
├─ types/                         # database.ts (supabase gen types 자동 생성)

│  ├─ migrations/                 # SQL 마이그레이션 (단일 진실)
│  ├─ seed.sql                    # detect_rules·penalty_rules·추가금 사전 시드
```

> **주의** Next 14는 TypeScript 설정 파일을 지원하지 않아 `next.config.mjs` 를 쓴다(`next.config.ts` 아님).
> ESLint는 flat config가 아니라 `.eslintrc.json` 이다(`eslint.config.mjs` 아님). 두 항목은 T-01에서 정정됐다.

### 구조 원칙
- **로직은 lib/core, 화면은 app·components**: AI 프롬프트·검증, 룰 엔진, 가격 계산, 마스킹은 lib/core에 격리(React/Next import 금지) — Expo 전환·테스트·재사용의 핵심. 전환 시 lib/core를 패키지로 승격. 이 금지는 `lib/core/no-framework-imports.test.ts` 가 강제한다.
- **DB 변경은 supabase/migrations로만**: 대시보드 수동 변경 금지, 마이그레이션 파일 커밋 후 `npm run db:types`로 타입 재생성.
- **환경 분리**: local(도커) → staging(Supabase 프로젝트 A + Vercel preview) → production(프로젝트 B). 키는 .env.local(.gitignore), 목록은 .env.example.
- **비밀·개인정보**: 서비스 롤 키·ANTHROPIC_API_KEY는 서버 전용. 클라이언트엔 publishable key만. 업로드 원문·경로를 로그에 남기지 않는다. 계약서 샘플은 _local_reports/samples(git 제외).
- **자산은 슬롯 id로만 참조**: 이미지·아이콘은 `lib/assets/manifest.ts` 의 슬롯 id로 참조하고 경로를 직접 쓰지 않는다. 실제 이미지 교체는 같은 경로 덮어쓰기만으로 끝난다. 규약은 **`docs/ASSETS.md`**(T-02c 구현 완료).
- **디자인 토큰은 globals.css + tailwind.config.ts**: 색·타이포·간격 토큰과 공통 컴포넌트 사용 규칙은 **`docs/DESIGN.md`**(T-04b 구현 완료).

## 3. 로컬 개발 환경 (Windows 기준)

### 필수 설치
| 도구 | 버전/비고 |
|---|---|
| Node.js | 실제 설치본 기준(06 §2 참조). nvm-windows로 버전 고정 권장 |
| Git | + GitHub 리포 `nomadconan/wedding` (main/dev 브랜치, PR 기반) |
| Docker Desktop | Supabase 로컬 스택 실행용 (WSL2 백엔드 활성화) |
| Supabase CLI | **devDependency로 설치돼 있으며 전역 PATH에 없다.** 반드시 **`npx supabase ...`** 로 호출한다 |
| GitHub CLI | `winget install --id GitHub.cli` (PR 작업용, 선택) |
| Android Studio | Capacitor 안드로이드 빌드 (SDK+에뮬레이터). JDK 17 |
| (iOS) | 로컬 macOS 없으면 클라우드 CI(Codemagic/EAS 등)로 빌드·배포 |
| VS Code | 확장: ESLint, Prettier, Tailwind, SQL 도구 |

### 최초 셋업 순서
```bat
:: 0) 리포 클론
git clone https://github.com/nomadconan/wedding.git wstory
cd wstory

:: 1) 의존성
npm install

:: 2) 환경변수
copy .env.example .env.local
:: → npx supabase status 출력의 URL/publishable key, ANTHROPIC_API_KEY, 토스 테스트 키 기입

:: 3) 로컬 Supabase 기동 + 마이그레이션·시드 + 타입 생성
npm run db:start
npm run db:reset
npm run db:types

:: 4) 웹 개발 서버
npm run dev            :: http://localhost:3000

:: (셋업 일괄 실행: scripts\dev-setup.bat)
```

> **Supabase CLI 호출** `npm run db:*` 스크립트는 내부적으로 `supabase` 를 부르며 npm이 `node_modules\.bin` 을 PATH에 넣어주므로 정상 동작한다.
> **터미널에서 직접 호출할 때는 반드시 `npx supabase ...`** 를 쓴다 — 전역 설치본이 없다.
> 예: `npx supabase status`, `npx supabase db diff -f <이름>`

### 일상 개발 플로우
1. `dev` 에서 기능 브랜치 생성 → 작업 → PR. 브랜치명: `feat|fix|chore|docs/<태스크ID>-<요약>`
2. DB 변경: 마이그레이션 SQL 작성 → `npm run db:reset` 으로 검증 → 커밋.
3. 타입 동기화: `npm run db:types` (types/database.ts 재생성).
4. 테스트: lib/core는 vitest 단위 테스트 필수(룰 엔진 경계값), E2E는 Playwright(미도입).
5. 커밋 전: `npm run lint && npm run test`.
6. 배포: Vercel(웹, preview→production), 앱은 웹 배포 반영 + 네이티브 변경 시에만 스토어 제출.

### AI 개발 시 로컬 주의
- Claude API 호출은 서버(Route Handler) 경유만 — 클라이언트 직접 호출 금지(키 노출).
- 프롬프트·룰(prompt_fragment)은 lib/core/rules에 코드로 관리(버전 태깅), DB detect_rules와 시드로 동기화.
- 로컬 테스트용 계약서 샘플은 `_local_reports/samples/`(gitignore, 개인정보 마스킹본만 커밋 허용).

## 4. 개발 단계별 앱 마일스톤

**07 §1.3의 8단계**에 맞춰 재매핑했다(v2.0, D-20). **단계별 공개는 없으며 전체 완성 후 일괄 오픈**하므로, 아래는 '출시 시점'이 아니라 **각 단계에서 앱 측에 준비해 둬야 할 것**이다.

| 단계 | 앱 측 준비 |
|---|---|
| 1 기반 | 반응형 셸을 **375px 모바일 퍼스트**로 설계(`ConsumerShell`). 웹뷰에서 그대로 동작하도록 애니메이션은 CSS transform 위주 |
| 2 공급 | **업체 어드민은 웹 전용 유지**(데스크톱 사용 맥락). 앱 래핑 대상에서 제외 |
| 3 수요 | PWA 매니페스트·오프라인 셸·홈화면 추가 배너. 장바구니·찜의 **커플 간 실시간 동기화**가 웹뷰에서 동작하는지 확인 |
| 4 연결 | **푸시 도입 지점** — FCM+APNs. 채팅(F-C-27)·상담 확정(F-C-29)·이행 확인 요청이 알림 대상이다. 백그라운드 알림 지연을 여기서 측정한다(Expo 전환 트리거) |
| 5 거래 | 결제 링크아웃 정책 검토. **디지털 멤버십은 웹 결제 유도**, 실물 서비스 예약 결제는 외부 PG 허용 대상. 전자서명 화면의 웹뷰 호환 확인 |
| 6 플래너 | 3자 일정·서명 알림 딥링크 |
| 7 AI·부가 | **카메라 도입 지점** — 계약서 촬영 업로드(@capacitor/camera, 클라이언트 리사이즈 ≤20MB). 공유 리포트 유니버설 링크·앱 링크 |
| 8 운영 | 운영자 콘솔은 웹 전용. Lighthouse 모바일 80+ 최종 확인 |
| 오픈 | **Capacitor Android 스토어 출시**(푸시+카메라), iOS는 클라우드 CI 빌드 제출 |

> **NOTE** 앱 필수 네이티브 기능 3종의 실제 도입 시점은 **4단계(푸시)·7단계(카메라)·오픈(스토어)** 이다. 그 전까지는 웹(PWA)만으로 개발·검증한다.
> **NOTE** Expo 전환 트리거 평가는 오픈 이후에 한다. 그 전에 전환을 검토하면 lib/core 격리 원칙만 지키면 되고 실제 데이터가 없다.
