**v2.0 변경 요약**

2. **플랫폼 지위 명시**(D-24). 통신판매중개자이며 **계약 당사자가 아니다.** 역할은 업체 관리·계약분쟁 조율·일정 관리다. §1.1·§6 공통 UI 규칙·§7.4에 반영했다.
3. **수수료 구조 확정**(D-16·D-17). 업체가 판매가를 등록하면 그 값이 그대로 고객 노출가이며, 플랫폼이 수수료를 제하고 정산한다. 요율은 **고정하지 않는다** — 업체별·카테고리별 차등이며 계약 시점 스냅샷으로 박힌다. 플래너는 카테고리별 부분 선택이고 선택 항목만 판매가의 일정 비율이 추가된다.
4. **신규 기능 13종**(D-19). 소비자 F-C-25~31(장바구니·찜·채팅·문의게시판·상담예약·조건검색·플래너 범위 선택), 업체 F-V-15~17, 운영자 F-A-15~17.
5. **계약 1건 + 결제 N회 분할**(D-21). 가계약/본계약으로 문서를 나누지 않는다. 분할 비율은 가변이며 초기 운영은 2회다. 플래너 수수료는 계약 성사 시 발생하고 유예 기간 경과 후 지급한다.
6. **상담·탐방 예약제 + 노쇼 보증금**(D-22). 이행 시 전액 환불, 노쇼 시 미환불. 금액은 가변 파라미터다. 이행 확인 규칙을 §3.11에 신설했다.
7. **증거 보존 체계**(D-23). `entity_events`(insert-only) 신설, `notifications`·`audit_logs` 확장. 모든 상태 변경과 알림 발송을 증적으로 남기고 책임 소재는 기록을 근거로 판단한다.
8. **§5.5 조건 기반 추천 신설.** 기존 §5.5~§5.7이 **§5.6~§5.8로 밀렸다.** 다른 문서에서 '§5.5 플래너 툴'을 참조하는 곳은 §5.6으로 읽어야 한다.
9. **§8 개발 일정 재작성.** M0~M9 마일스톤을 §1.3의 8단계에 맞춰 다시 썼다.

> **NOTE** 요율·분할 비율·유예 기간·보증금액의 **구체적 수치는 이 문서에 확정하지 않는다.** 전량 DB 파라미터이며 미설정 시 전역 기본값으로 폴백한다(§7.4). 표에 등장하는 숫자는 전부 '(예시)' 표기가 붙은 이해용 값이다.

## 1. 시스템 개요

### 1.1 문서 목적과 범위

본 문서는 웨딩클리어 플랫폼의 구현 기준을 정의한다. 기획서(사업 논리)와 코드(구현) 사이의 단일 참조점이며, Claude Code 작업 시 리포지토리 docs/ 하위에 사본을 동기화해 프롬프트 근거로 사용한다.

| **구분** | **포함**                                                      | **제외**                                                                      |
|----------|---------------------------------------------------------------|-------------------------------------------------------------------------------|
| 기능     | 소비자 앱·웹, 업체 어드민, 운영자 콘솔 전 기능 (D-09 풀개발)  | P4 확장 사업(컴플라이언스 SaaS 외판, 금융 제휴, 데이터 상품) — 설계 훅만 확보 |
| 기술     | 데이터 모델, API, AI 파이프라인, 화면 라우트, 비기능 요구사항 | UI 비주얼 디자인(별도 디자인 시스템 문서 `docs/DESIGN.md`), 인프라 IaC 상세   |
| 사업     | 개발 순서(§1.3)와 공급 우선 전략                              | 요율·분할 비율·유예 기간·보증금액의 **구체적 값**, 표준계약서 조항 문안(O-03) — 전량 DB 파라미터·플레이스홀더로 분리 |

#### 플랫폼의 지위와 역할 (D-24)

**웨딩클리어는 통신판매중개자이며 계약 당사자가 아니다.** 계약은 고객과 업체 사이에 체결되고, 플래너가 선택된 경우 플래너가 서명 당사자로 추가된다(§3.4).

| **역할** | **내용** |
|---|---|
| 업체 관리 | 입점 심사, 판매가·추가금 사전 등록 강제, 컴플라이언스 진단, 이상 가격 탐지 |
| 계약분쟁 조율 | 표준계약서 조항을 기준으로 위약금 청구·지불 절차를 진행한다. 플랫폼은 **판정자가 아니라 조율자**다 |
| 일정 관리 | 상담·탐방 예약, 3자 일정 공유, 이행 확인, 노쇼 처리 |

이 지위는 화면에도 고지한다(§6 공통 UI 규칙). 분쟁 처리 원칙은 §7.4에 있다.

> **NOTE** 서비스의 본질은 **업체와 고객의 직접 연결**이다(D-18). 플래너는 선택적 보조이고, 계약 검토·AI 플래너는 신뢰를 보조하는 부가 기능이다. 화면 위계에서 주인공은 **가격**이며, UI 톤은 **토스 계열**(무채색 + 단일 강조색, 넉넉한 여백, 큰 금액)이다 — 이 원칙이 §6 공통 UI 규칙과 `docs/DESIGN.md`를 지배한다.

> **NOTE** 리포 구조 주의: 프로젝트 지침 본문에 남아 있는 'Turborepo+pnpm 모노레포'는 D-07 시점 기술이며, D-08(단일 Next.js 앱, saju 스타일)로 대체되었다. 본 명세서는 D-08 및 05·06 문서를 따른다.

계층별 구성은 아래와 같다. 모든 계층은 05 문서의 폴더 구조와 1:1로 대응한다.

| **계층**          | **구성**                                                                             | **핵심 제약**                                        |
|-------------------|--------------------------------------------------------------------------------------|------------------------------------------------------|

| 클라이언트(앱)    | Capacitor 래핑(Android 우선, iOS는 클라우드 CI). 원격 URL 모드 + 코어 화면 정적 내장 | 네이티브 필수 3종: 카메라·푸시·스토어 입점           |
| 애플리케이션 서버 | Next.js Route Handlers (app/api/**), Vercel icn1 리전                              | AI·결제·서비스롤 키 사용은 전부 이 계층에서만        |
| 배치·비동기       | Supabase Edge Functions + Vercel Cron                                                | 문서 파기, D-day 알림, 참가격 지수 재계산, 정산 집계 |

| 결제              | 토스페이먼츠(분할 결제 회차·노쇼 보증금·멤버십), 에스크로는 O-03 확정 후 연동        | 앱 인앱결제 정책 회피 설계(웹 결제 링크아웃)         |
| 알림              | FCM + APNs(Capacitor Push), 이메일, 알림톡                                           | 토픽: D-day / 일정 변경 / 계약 단계 / 케어           |

#### 데이터 흐름 요약

- 소비자 요청 → RSC/Route Handler → Supabase(RLS로 본인·커플 범위 제한) → 응답

- AI 요청 → Route Handler → 마스킹·전처리 → Claude API → zod 검증 → 원문 대조 → 구조화 결과만 DB 저장 → 원문 파기 예약

- 업체 요청 → Route Handler → vendor_id 스코프 RLS → 상품·재고·가격·정산 데이터

- 운영자 요청 → admin 전용 Route Handler(서비스롤) → 전 범위 조회 + audit_logs 필수 기록

### 1.3 개발 순서 (8단계)

**단계별 공개는 하지 않는다. 전체를 완성한 뒤 일괄 오픈한다**(D-20). 아래 번호는 공개 순서가 아니라 **개발 착수 순서**이며, 각 기능 명세·API·화면의 '단계' 열은 이 번호를 따른다.

순서의 원칙은 **공급 우선**이다. 업체와 상품이 없으면 소비자 화면에 보여줄 것이 없고, 연결·거래 기능은 양쪽이 다 있어야 검증되기 때문이다.

| 단계 | 이름 | 범위 | 선행 |
|---|---|---|---|
| 1 | 기반 | 디자인 시스템, 공통 컴포넌트, 레이아웃 셸 | — |
| 2 | 공급 | 업체 입점·심사·상품 등록·추가금 사전표·업체 어드민 전반 | 1 |
| 3 | 수요 | 회원가입·온보딩·커플 연동·탐색·필터·비교·장바구니·찜 | 1, 2 |
| 4 | 연결 | 실시간 채팅·문의게시판·전화 연결·상담/탐방 예약·일정 3자 공유 | 2, 3 |
| 5 | 거래 | 표준계약·3자 서명·결제 2회 분할·정산·환불·위약금 | 4 |
| 6 | 플래너 | 플래너 등록·부분 선택 과금·랭킹·권한 위임 | 5 |
| 7 | AI·부가 | 조건 검색 + 대화형 AI 추천, 계약 검토, 위약금 시뮬레이터, 예산, 체크리스트 | 3, 5 |
| 8 | 운영 | 운영자 콘솔·분쟁 조율·CI·품질·모니터링 | 2~7 |

**단계 간 의존은 '착수 가능 시점'이지 '완료 대기'가 아니다.** 예컨대 7단계 AI·부가는 3단계 탐색 데이터 구조가 확정되면 5단계와 병행 착수할 수 있다.

> **NOTE** `feature_flags`(§3.8)는 **릴리즈 스위치가 아니다.** 단계별 공개를 폐기했으므로 플래그의 역할은 두 가지로 좁혀진다 — ① 부분 공개(지역·사용자 세그먼트 대상 제한 오픈), ② **긴급 롤백**(장애 시 특정 기능만 격리). 범위 축소 금지 원칙(D-09)은 그대로다: 기능을 빼는 것이 아니라 만들어 두고 켜지 않는다.

> **NOTE** 이전 버전의 R1/R2/R3 릴리즈 구분은 폐기됐다. 다른 문서에 남아 있는 'R1 기능', 'R2에서 공개' 같은 표현은 **낡은 정보**이며 위 단계 번호로 읽어야 한다.

#### 요율 해석 규칙

```
요율 조회(대상, 카테고리, 시점)
  1) scope_type='vendor'   AND scope_key=업체id   AND 시점이 effective 구간 내  → 있으면 채택
  2) scope_type='category' AND scope_key=카테고리 AND 시점이 effective 구간 내  → 있으면 채택
  3) scope_type='global'                          AND 시점이 effective 구간 내  → 채택
  (플래너 요율도 planner → category → global 순서로 동일하게 해석한다)
```

- **좁은 범위가 넓은 범위를 이긴다.** 업체별 > 카테고리별 > 전역.
- `effective_from` / `effective_to` 로 **시점 기준 조회**한다. 요율 변경은 새 행 추가이며 기존 행을 수정하지 않는다 — 과거 시점 조회가 가능해야 정산 이의 제기에 답할 수 있다.
- 값은 **basis point 정수**(1% = 100bp)로 저장한다. 부동소수점을 쓰지 않으며 `lib/core/pricing` 의 기존 방식과 동일하다.
- **어느 단계에서도 조회 결과가 없으면 안 된다.** `global` 행은 항상 존재해야 하며, 없으면 계약 확정을 막고 운영자에게 경보한다.

### 3.11 이행 확인 · 노쇼 처리 규칙

상담·탐방(F-C-29)의 보증금은 **이행 여부에 따라 환불 또는 몰취**된다(D-22). 판정은 사람의 재량이 아니라 아래 규칙으로 한다.

#### 확인 절차

| **순서** | **처리** |
|---|---|
| 1 | 예정 시각(`scheduled_at`)이 경과하면 **고객·업체 양측에 이행 확인을 요청**한다. 요청 발송은 `notifications` 에 기록된다 |
| 2 | 양측 응답이 **일치**하면 자동 처리한다 — 이행이면 **자동 환불**, 노쇼면 **자동 몰취** |
| 3 | 응답이 **불일치**하거나 한쪽이라도 기한 내 **무응답**이면 `status='disputed'` 로 전환하고 **운영자 조율 큐**(F-A-16)로 이관한다 |
| 4 | 조율 결정은 `consultation_deposits.resolution_reason` 과 `resolved_by` 에 기록하고, 근거 이벤트 id를 `audit_logs.resolution_basis` 에 남긴다 |

#### 판정 규칙

| **상황** | **결과** | **근거** |
|---|---|---|
| 양측 모두 이행 확인 | 보증금 **전액 환불** | — |
| 양측 모두 고객 노쇼 확인 | 보증금 **몰취** | — |
| 양측 모두 업체 노쇼 확인 | 보증금 **전액 환불** + 업체 페널티 검토 | 업체 귀책 |
| 응답 불일치 | `disputed` → 운영자 조율 | 증적 타임라인으로 판단 |
| **양측 모두 기한 내 무응답** | **환불**(기본값) | **고객 보호 우선.** 몰취가 기본이면 업체가 확인을 방치하는 것이 이득이 되는 구조가 되기 때문이다 |
| 예정 시각 **N시간 전까지의 취소** | **노쇼가 아님 → 전액 환불** | `N` 은 `app_settings` 파라미터 |

> **NOTE** 무응답 기본값을 환불로 두는 것이 이 규칙의 핵심 설계다. 기본값이 몰취면 업체는 아무것도 하지 않는 편이 유리해지고, 그러면 확인 절차 자체가 형해화된다. 기본값은 **방치가 이득이 되지 않는 방향**으로 정한다.

> **NOTE 파라미터** 보증금액, 이행 확인 응답 기한, 취소 무료 기한(N시간)은 **전부 `app_settings` 파라미터**이며 이 문서에 값을 확정하지 않는다(§7.4).

## 4. API 명세

### 4.1 공통 규약

- 모든 엔드포인트는 app/api/** Route Handler로 구현한다. 클라이언트에서 Claude API·서비스롤 키 직접 호출 금지.

- 요청·응답 본문은 lib/core/schemas의 zod 스키마로 양방향 검증한다. 검증 실패는 422로 반환한다.

- 응답 포맷: { ok: boolean, data?: T, error?: { code, message, details? } }. 에러 코드는 도메인 접두어 사용(AUTH_, DOC_, PAY_, AI_).

- 인증은 Supabase Auth 세션 쿠키. 권한 판정의 최종 경계는 RLS이며 핸들러 체크는 보조다.

- 쓰기 요청은 Idempotency-Key 헤더를 지원한다(결제·예약·AI 생성 필수).

- 레이트리밋: AI 계열은 사용자·플랜 단위, 공개 조회는 IP 단위. 초과 시 429와 재시도 시각 반환.

- 장시간 작업(문서 분석)은 202로 job id를 반환하고 상태 폴링 또는 SSE로 진행률을 전달한다.

## 5. AI 파이프라인

### 5.1 공통 원칙

- 호출 위치: app/api/** 서버 전용. 프롬프트·스키마·룰은 lib/core에 코드로 관리하고 버전 태깅한다.

- 출력은 반드시 zod 스키마로 검증한다. 실패 시 1회 재시도(스키마 오류 피드백 포함), 재실패 시 사용자에게 '분석 실패'를 반환하고 부분 결과를 노출하지 않는다.

- 사실 주장은 원문 인용 대조 검증을 통과해야 한다. 원문에 존재하지 않는 조항 인용은 해당 finding을 폐기한다(할루시네이션 차단).

- 개인정보는 전달 전 마스킹한다. 마스킹 실패 시 호출 자체를 중단하고 F-A-08 경보를 발생시킨다.

- 모든 AI 결과 화면에는 '참고 정보이며 법률 자문이 아님' 고지와 근거(표준약관·소비자분쟁해결기준 조항)를 병기한다.

- 결정적 계산(위약금·총액·수수료)은 LLM을 사용하지 않고 lib/core/pricing의 순수 함수로 처리한다.

### 5.2 계약서 검토 파이프라인 (F-C-07) — 8단계

| **단계**        | **처리**                                                                          | **구현 위치**                    | **실패 시**                        |

### 5.3 위약금 시뮬레이터 (F-C-08)

LLM을 사용하지 않는다. penalty_rules(소비자분쟁해결기준 기반)와 계약서에서 추출된 조항을 입력으로 lib/core/pricing/penalty.ts가 결정적으로 계산한다.

- 입력: 카테고리, 총액, 계약금, 예식일, 취소 시점, 계약서 규정 위약률

- 출력: 기준 위약금, 계약서 기준 위약금, 초과분, 근거 조항, 이의 제기 문구

- 경계값(취소 시점 구간 경계, 계약금 반환 여부)은 vitest 단위 테스트 필수 — 05 §3 개발 플로우

### 5.5 조건 기반 추천 (F-C-30)

"0월 0일 강남 300인" 같은 **자연어와 조건이 섞인 입력**을 구조화 조건으로 바꾼 뒤, **DB 필터 조회로 후보를 만들고 랭킹**한다. 추천 결과 자체를 LLM이 지어내지 않는다.

| **단계** | **처리** | **구현 위치** | **실패 시** |
|---|---|---|---|
| 1. 파싱 | 자연어+조건 혼합 입력 → 구조화 조건(날짜·지역·하객수·예산·스타일). zod 스키마로 검증 | Claude API(서버) + lib/core/schemas | 파싱 실패 시 해당 조건을 비우고 사용자에게 직접 선택을 요청 |
| 2. 조회 | 구조화 조건으로 **DB 필터 조회**. 가용 슬롯·판매가·지역·수용 인원 기준 | Route Handler | 결과 0건이면 조건 완화 제안(가격대·날짜 범위) |
| 3. 랭킹 | 조건 부합도 기준 정렬 | lib/core | — |
| 4. 노출 | **랭킹 기준 코드를 응답과 화면에 함께 노출**한다 | API 응답 + UI 배지 | 기준 코드 없는 응답은 반환하지 않는다 |

- **랭킹 기준을 숨기지 않는다**(D-03). 광고·제휴 수익이 없는 구조를 화면으로 증명하는 것이 이 서비스의 차별성이므로, 정렬·추천 결과에는 예외 없이 기준 배지를 붙인다(§6 공통 UI 규칙).
- 기존 가드레일을 그대로 유지한다: **조회 결과에 없는 수치를 생성하지 않는다.** 가격·업체 사실 주장은 반드시 2단계 조회 결과에 근거해야 하며, 응답 후처리에서 검사한다.
- 파싱 결과는 사용자에게 **되돌려 보여주고 수정 가능하게** 한다. "강남 / 2027-03-14 / 300인"처럼 칩으로 노출해 오해석을 사용자가 바로잡을 수 있어야 한다.

| summarize_report         | 기존 계약 검토 리포트 요약 조회                      | 읽기          |

#### 플래너 가드레일

- 법률·세무·의료 판단 요청은 일반 정보 제공 + 전문가 상담 안내로 처리하고 확정적 결론을 내리지 않는다.

- 가격·업체 사실 주장은 반드시 툴 조회 결과에 근거해야 하며, 미조회 상태의 수치 생성은 금지한다(프롬프트 제약 + 응답 후처리 검사).

- 결제·계약 서명 등 되돌릴 수 없는 행위는 툴로 실행하지 않고 화면 이동만 제안한다.

- 특정 업체 편향 추천 금지 — 광고·제휴가 없는 구조(D-03)이므로 정렬·추천 기준을 응답에 함께 노출한다.

- 무료 사용자 일일 턴 제한, 세션당 토큰 상한, 남용 탐지 시 레이트리밋.

### 5.7 가격 이상 탐지 (F-A-14)

업체 등록가·실거래가·참가격 지수 간 편차를 배치로 분석한다. 판정 기준(가정): 동일 지역·카테고리·하객 구간에서 등록가가 지수 중앙값 대비 40% 이상 낮으면서 실제 성사 건이 없으면 '미끼 의심', 계약 총액이 견적 총액 대비 25% 초과 시 '추가금 과다' 플래그를 운영 큐에 적재한다. 임계값은 app_settings로 관리하여 데이터 축적 후 조정한다.

#### 공통 UI 규칙

- **화면의 주인공은 가격이다**(D-18). **총액을 화면에서 가장 크게 표시**하고, **추가금·플래너 수수료 포함 여부를 같은 블록에서 확인**할 수 있게 한다. 사용자가 스크롤해야 추가금을 발견하는 구조는 규칙 위반이다.

- **UI 톤은 토스(toss.im) 계열**(D-18) — **무채색 기반 + 단일 강조색**, **넉넉한 여백**, **금액을 크고 굵게**(단위는 작게), **화면당 정보량 최소화**, **한 화면 한 질문**. 강조색은 "지금 눌러야 할 것" 하나에만 쓴다. 구현 토큰과 컴포넌트 규칙은 `docs/DESIGN.md`에 있다.

- **플랫폼은 통신판매중개자이며 계약 당사자가 아님을 거래 관련 화면에 고지한다**(D-24). 대상: 계약·결제·상담 예약·분쟁 관련 화면.

- 모바일 퍼스트. 소비자 화면은 375px 기준 설계, 업체·운영자 콘솔은 데스크톱(1280px) 기준으로 하되 반응형 대응.

- **한 화면 한 질문.** 온보딩 6단계는 단계당 입력 하나만 둔다. 진행률을 보여주고 되돌아갈 수 있게 한다.

- AI 결과가 포함된 모든 화면에 '참고 정보이며 법률 자문이 아님' 고지를 고정 노출한다.

- 가격 표시는 항상 총액(부가세 포함 여부 명시) 기준이며, 추가금은 동일 화면에서 확인 가능해야 한다.

- **업체 상품 등록 화면에는 "등록 판매가가 고객 노출가이며 여기서 수수료를 제한 금액이 정산된다"를 상시 표시**한다(D-16, F-V-03).

- 목록은 가상화, 이미지는 lazy, 애니메이션은 CSS transform 위주(WebView 성능 가드, 05 §1).

- 로딩·빈 상태·에러 상태 3종을 모든 데이터 화면에 정의한다.

- 정렬·추천 결과에는 기준 배지를 노출한다(유료 노출 없음을 UI에서 증명).

### 7.2 보안

- 전 테이블 RLS 활성화. 서비스롤 키는 Route Handler·Edge Function 전용이며 클라이언트 번들 유입 여부를 CI에서 검사한다.

- Storage 접근은 서명 URL(유효 5분)로만. 버킷 공개 설정은 vendor-media 외 금지.

- 결제 웹훅은 서명 검증 후 처리하고, 멱등 키로 중복 반영을 차단한다.

- 인증은 Supabase Auth 세션 쿠키(HttpOnly, Secure, SameSite=Lax). 운영자 계정은 2단계 인증 필수.

- 의존성 취약점 스캔(npm audit)과 시크릿 스캔을 PR 파이프라인에 포함한다.

- admin·vendor의 상태 변경 액션은 예외 없이 audit_logs에 기록한다.

### 7.4 신뢰성 · 운영

- 환경 3단 분리: local(Docker) → staging(Supabase 프로젝트 A + Vercel Preview) → production(프로젝트 B).

- DB 백업: Supabase 자동 백업 + 마이그레이션 기반 재구성 가능성 상시 유지(supabase/migrations 단일 진실).

- 장애 대응: Sentry 알림 → 피처 플래그로 해당 기능 격리 → 롤백. AI 장애 시 도구 화면은 '일시 이용 불가' 상태로 degrade하고 나머지 기능은 유지한다.

- 외부 의존성 실패 처리: Claude API·토스·알림톡 각각 타임아웃·재시도·서킷브레이커 정책을 정의한다.

- 배치 실패는 job_runs에 기록하고 파기 배치 실패는 즉시 경보(개인정보 사고 직결).

#### 분쟁 처리 원칙 (D-23 · D-24)

- **모든 상태 변경과 알림 발송을 증적으로 남긴다.** 상태 전이는 `entity_events`(insert-only), 알림은 `notifications` 의 발송·도달·열람 시각으로 기록한다. 기록되지 않은 사실은 분쟁에서 주장할 수 없다는 전제로 설계한다.

- **책임 소재는 기록을 근거로 판단한다.** 절차는 **양측 확인 → 불일치 시 운영자 조율 → 결정 기록**이다(§3.11). 결정에는 근거 이벤트 id를 반드시 첨부한다.

- **플랫폼은 판정자가 아니라 조율자다**(D-24). 통신판매중개자로서 표준계약서 조항을 기준으로 절차를 진행할 뿐, 계약 당사자로서 책임을 지거나 법적 판단을 내리지 않는다.

#### 가변 파라미터 원칙

**다음 값을 코드에 하드코딩하지 않는다.** 전량 DB에서 조회하며, 미설정 시 전역 기본값으로 폴백한다.

| **파라미터** | **저장 위치** | **해석** |
|---|---|---|
| 업체 수수료 요율 | `commission_rates` | 업체 → 카테고리 → 전역 (§3.8) |
| 플래너 수수료 요율 | `planner_fee_rates` | 플래너 → 카테고리 → 전역 |
| 결제 분할 비율·회차 | `payment_schedules.ratio_bp` | 계약별로 결정. 초기 운영은 2회 |
| 플래너 지급 유예 기간 | `app_settings` | 계약 성사 후 지급까지의 대기 기간 |
| 노쇼 보증금액 | `app_settings` | 유형(방문상담·탐방)별로 다를 수 있다 |
| 이행 확인 응답 기한 · 취소 무료 기한 | `app_settings` | §3.11 |

- **개발·테스트는 이 값들이 미확정인 상태에서도 진행 가능해야 한다.** 값이 없으면 전역 기본값을, 그것도 없으면 개발용 기본값을 쓰되 **운영 환경에서는 전역 행이 없으면 계약 확정을 막고 경보**한다.
- 요율은 **basis point 정수**로 다룬다. 부동소수점 연산을 쓰지 않는다(`lib/core/pricing` 규약과 동일).
- **요율 변경은 소급되지 않는다.** 기존 계약은 `bookings` 의 스냅샷 값을 계속 사용한다(§3.4).

### 7.6 앱 (Capacitor)

- 원격 URL 모드 기본, 코어 화면은 정적 내장으로 심사 리스크 완화(05 §1).

- 네이티브 기능 3종: 카메라(@capacitor/camera, 업로드 전 클라이언트 리사이즈 ≤20MB), 푸시(FCM+APNs), 스토어 입점.

- 디지털 멤버십 결제는 스토어 정책 준수(웹 결제 링크아웃). 실물 서비스 예약 결제는 외부 PG 허용 범위로 처리.

- 딥링크: 공유 리포트·커플 초대용 유니버설 링크·앱 링크 설정.

- iOS는 로컬 macOS 부재 전제로 클라우드 CI 빌드·배포(05 §3).

### 7.7 법적 표현 원칙

- AI 검토·진단 결과에는 항상 '참고 정보이며 법률 자문이 아님'을 병기하고 근거 조항(표준약관·소비자분쟁해결기준)을 함께 제시한다.

- 위약금 계산은 '기준 대비 비교값'으로 표현하며 확정적 법적 결론이나 승소 가능성을 언급하지 않는다.

- 업체에 대한 부정적 판단은 사실(등록가·계약 내역)과 기준 대비 편차로만 표현하고, 평가적 단정 표현을 사용하지 않는다.

- 검증 후기는 거래 이력 기반임을 표기하고, 삭제·비공개 처리 기준을 공개한다.

- **플랫폼의 지위를 오인시키지 않는다.** 통신판매중개자이며 계약 당사자가 아님을 거래 관련 화면에 고지하고(§6), 플랫폼이 이행이나 품질을 보증하는 것처럼 읽히는 표현을 쓰지 않는다(D-24).

#### 표준계약서 조항 (O-03 대기)

- **표준계약서의 조항 문안은 O-03 법무 검수 전까지 확정하지 않는다.**

- 개발 단계에서는 **템플릿 구조·서명 플로우·당사자 정의만 구현**하고 **조항 본문은 플레이스홀더**로 둔다. 조항 번호를 임의로 부여하지 않는다 — `lib/core/rules` 의 `basis_ref` 가 같은 이유로 출처 수준까지만 적고 있다.

- **위약금 청구·지불은 표준계약서 조항에 근거하며**, 금액 산정은 `lib/core` 의 결정적 계산(§5.3)을 따른다. LLM이 위약금을 산출하지 않는다.

- 산정 결과는 '기준 대비 비교값'으로 제시하고 근거를 함께 노출한다. 확정적 법적 결론을 내리지 않는다.
