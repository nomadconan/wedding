## 1. 시스템 개요

### 1.1 문서 목적과 범위

본 문서는 웨딩클리어 플랫폼의 구현 기준을 정의한다. 기획서(사업 논리)와 코드(구현) 사이의 단일 참조점이며, Claude Code 작업 시 리포지토리 docs/ 하위에 사본을 동기화해 프롬프트 근거로 사용한다.

| **구분** | **포함**                                                      | **제외**                                                                      |
|----------|---------------------------------------------------------------|-------------------------------------------------------------------------------|
| 기능     | 소비자 앱·웹, 업체 어드민, 운영자 콘솔 전 기능 (D-09 풀개발)  | P4 확장 사업(컴플라이언스 SaaS 외판, 금융 제휴, 데이터 상품) — 설계 훅만 확보 |
| 기술     | 데이터 모델, API, AI 파이프라인, 화면 라우트, 비기능 요구사항 | UI 비주얼 디자인(별도 디자인 시스템 문서), 인프라 IaC 상세                    |
| 사업     | 릴리즈 순서와 콜드스타트 매핑                                 | 수수료 요율 확정(O-02), 에스크로 법무 결론(O-03) — 파라미터로 분리            |

> **NOTE** 리포 구조 주의: 프로젝트 지침 본문에 남아 있는 'Turborepo+pnpm 모노레포'는 D-07 시점 기술이며, D-08(단일 Next.js 앱, saju 스타일)로 대체되었다. 본 명세서는 D-08 및 05·06 문서를 따른다.

### 1.2 시스템 아키텍처

계층별 구성은 아래와 같다. 모든 계층은 05 문서의 폴더 구조와 1:1로 대응한다.

| **계층**          | **구성**                                                                             | **핵심 제약**                                        |
|-------------------|--------------------------------------------------------------------------------------|------------------------------------------------------|
| 클라이언트(웹)    | Next.js App Router — RSC 기본, 인터랙션 구간만 클라이언트 컴포넌트                   | SEO 페이지는 SSG/ISR, 소비자 도구는 SSR+CSR 혼합     |
| 클라이언트(앱)    | Capacitor 래핑(Android 우선, iOS는 클라우드 CI). 원격 URL 모드 + 코어 화면 정적 내장 | 네이티브 필수 3종: 카메라·푸시·스토어 입점           |
| 애플리케이션 서버 | Next.js Route Handlers (app/api/**), Vercel icn1 리전                              | AI·결제·서비스롤 키 사용은 전부 이 계층에서만        |
| 배치·비동기       | Supabase Edge Functions + Vercel Cron                                                | 문서 파기, D-day 알림, 참가격 지수 재계산, 정산 집계 |
| 도메인 로직       | lib/core (rules · pricing · schemas)                                                 | React/Next import 금지. vitest 단위 테스트 필수      |
| 데이터            | Supabase PostgreSQL(RLS 전면) + Auth + Storage                                       | 환경 3단: local(Docker) → staging → production       |
| AI                | Claude API(서버 전용). 프롬프트·zod 스키마는 lib/core에서 버전 관리                  | 클라이언트 직접 호출 금지                            |
| 결제              | 토스페이먼츠(예약금·잔금·멤버십), R3에서 에스크로 연동                               | 앱 인앱결제 정책 회피 설계(웹 결제 링크아웃)         |
| 알림              | FCM + APNs(Capacitor Push), 이메일, 알림톡                                           | 토픽: D-day / 일정 변경 / 계약 단계 / 케어           |
| 관측              | Sentry(에러) + Vercel Analytics + 자체 ai_call_logs                                  | AI 토큰·지연·검증 실패율 추적                        |

#### 데이터 흐름 요약

- 소비자 요청 → RSC/Route Handler → Supabase(RLS로 본인·커플 범위 제한) → 응답

- AI 요청 → Route Handler → 마스킹·전처리 → Claude API → zod 검증 → 원문 대조 → 구조화 결과만 DB 저장 → 원문 파기 예약

- 업체 요청 → Route Handler → vendor_id 스코프 RLS → 상품·재고·가격·정산 데이터

- 운영자 요청 → admin 전용 Route Handler(서비스롤) → 전 범위 조회 + audit_logs 필수 기록

### 1.3 릴리즈 단계 정의 (콜드스타트 4단계 매핑)

개발은 전 범위를 병행 진행하되, 공개는 아래 순서로 한다. 각 기능 명세의 '릴리즈' 열은 이 정의를 따른다.

| 릴리즈 | 콜드스타트 단계 | 공개 시점 | 핵심 공개 기능 | 성공 판정 지표(가정) |
|---|---|---|---|---|
| R1 | P1 수요 선확보 / (공급 불필요) | M1~M4 | AI 플래너 '클리어', 계약서 검토 리포트, 위약금 시뮬레이터, 참가격 인덱스, 예산·체크리스트, SEO 콘텐츠, 멤버십 가입 | MAU, 리포트 생성수, SEO 유입, 멤버십 전환율 |
| R2 | P2 절박한 공급 / (비수기·평일·지방) | M5~M8 | 업체 입점·실재고 캘린더·다이내믹 프라이싱, 직거래 문의·견적, 예약금 결제, 정산 집계, 컴플라이언스 진단 | 입점 업체수, 문의→예약 전환율, GMV |
| R3 | P3 거래 표준 | M9~M12 | 전자계약·서명, 에스크로 안전거래, 검증 후기, 플래너 마켓, 자동 정산, 분쟁 중재 | 에스크로 거래 비중, 분쟁률, 재방문율 |
| R4 | P4 확장 | 범위 표기만 | 컴플라이언스 SaaS 외판, 금융 제휴, 데이터 상품 | 본 명세서 범위 외(설계 훅만 확보) |

> **NOTE** 범위 축소 금지 원칙(D-09)의 구현 방식: R2·R3 기능도 R1과 동시에 개발·테스트하며, 피처 플래그(feature_flags 테이블, §3.9)로 공개 시점만 제어한다. '나중에 만든다'가 아니라 '만들어 두고 켜지 않는다'.

| admin          | 운영 관리자     | 전 권한 + 룰·프롬프트 버전 배포, 정산 집행, 권한 관리                     | R1       |

## 2. 전체 기능 명세 (3면)

기능 ID 체계: F-C(소비자) / F-V(업체 어드민) / F-A(운영자 콘솔). 각 기능은 화면 명세(§6)·API 명세(§4)와 ID로 연결된다.

### 2.1 소비자 (Consumer) — 24기능

| ID | 기능 | 상세 요구사항 | 릴리즈 |
|---|---|---|---|
| F-C-01 | 회원가입·온보딩 | 소셜(카카오/네이버/구글/애플)+이메일. 온보딩 6문항: 예식 예정일, 지역, 예산 총액, 하객 규모, 스타일 선호, 진행 단계. 결과로 couples 레코드와 초기 체크리스트 자동 생성 | R1 |
| F-C-02 | 커플 연동 | 초대 코드·딥링크로 배우자 연동. 동일 couple_id 데이터 공유, 활동 로그에 작성자 표기 | R1 |
| F-C-03 | AI 플래너 '클리어' 대화 | 스트리밍 채팅. 커플 프로필·예산·진행 상태를 컨텍스트 주입. 툴 호출로 실제 데이터 조회·생성(§5.5). 무료 일일 턴 제한, 멤버십 무제한 | R1 |
| F-C-04 | 일정·체크리스트 자동 생성 | 예식일 역산 D-360~D-0 태스크 자동 생성(카테고리: 홀·스드메·예단·혼수·서류·허니문). 수동 추가·기한 변경, 완료율 시각화, 담당자 지정 | R1 |
| F-C-05 | 예산 배분·추적 | 총예산 입력 → 카테고리별 권장 배분(참가격 지수 기반) → 실지출 등록·초과 경고. 견적·계약 확정 시 자동 반영 | R1 |
| F-C-06 | 견적 비교·정규화 | 이미지/PDF/텍스트 견적 업로드 → 항목 표준 카테고리 매핑 → 추가금 사전표 반영한 '실총액' 환산 → 2~5개 병렬 비교표 | R1 |
| F-C-07 | 계약서 검토 리포트 | 촬영·파일 업로드 → 마스킹 → 검출 룰 20종 + LLM 분석 → 위험 조항별 등급·근거 조항·협상 문구. '법률 자문 아님' 상시 병기. 원문 24시간 내 파기 | R1 |
| F-C-08 | 위약금 시뮬레이터 | 계약금·총액·예식일·취소 시점 입력 → 소비자분쟁해결기준 대비 계약서 조항 비교, 초과분 산출. 결정적 계산(LLM 미사용) | R1 |
| F-C-09 | 참가격 인덱스 탐색 | 지역·카테고리·하객수·시즌별 가격 분포(중앙값·사분위). 출처·표본수·수집일 표기. R2부터 실거래가 기반 갱신 | R1 |
| F-C-10 | 업체 탐색·필터·비교 | 홀/스드메/기타 카탈로그. 필터: 지역·예산·하객수·날짜·스타일. 정렬 기준 공개(광고·유료 노출 없음 명시). 최대 4개 비교표 | R1 카탈로그 / R2 실재고 |
| F-C-11 | 실시간 예약 가능일 | 업체 캘린더 연동. 날짜 선택 시 시간대별 잔여 슬롯과 해당 조건 가격 즉시 표시 | R2 |
| F-C-12 | 다이내믹 가격 노출 | 비수기·평일·지방·임박 할인 룰이 적용된 최종가와 정가 대비 할인율 표시. 할인 사유 라벨 노출 | R2 |
| F-C-13 | 직거래 문의·견적 요청 | 1:N 문의(최대 5개 업체 동시). 표준 요청 폼(날짜·하객수·필수 옵션)으로 견적 형식 통일. 응답 SLA 표시 | R2 |
| F-C-14 | 예약금 결제 | 토스페이먼츠. 예약금 결제 → 가예약 홀드 → 업체 승인 시 확정. 취소·환불 규정 결제 전 고지 및 동의 로그 저장 | R2 |

## 4. API 명세

### 4.1 공통 규약

- 모든 엔드포인트는 app/api/** Route Handler로 구현한다. 클라이언트에서 Claude API·서비스롤 키 직접 호출 금지.

- 요청·응답 본문은 lib/core/schemas의 zod 스키마로 양방향 검증한다. 검증 실패는 422로 반환한다.

- 응답 포맷: { ok: boolean, data?: T, error?: { code, message, details? } }. 에러 코드는 도메인 접두어 사용(AUTH_, DOC_, PAY_, AI_).

- 인증은 Supabase Auth 세션 쿠키. 권한 판정의 최종 경계는 RLS이며 핸들러 체크는 보조다.

- 쓰기 요청은 Idempotency-Key 헤더를 지원한다(결제·예약·AI 생성 필수).

- 레이트리밋: AI 계열은 사용자·플랜 단위, 공개 조회는 IP 단위. 초과 시 429와 재시도 시각 반환.

- 장시간 작업(문서 분석)은 202로 job id를 반환하고 상태 폴링 또는 SSE로 진행률을 전달한다.

## 5. AI 파이프라인

### 5.1 공통 원칙

- 호출 위치: app/api/** 서버 전용. 프롬프트·스키마·룰은 lib/core에 코드로 관리하고 버전 태깅한다.

- 출력은 반드시 zod 스키마로 검증한다. 실패 시 1회 재시도(스키마 오류 피드백 포함), 재실패 시 사용자에게 '분석 실패'를 반환하고 부분 결과를 노출하지 않는다.

- 사실 주장은 원문 인용 대조 검증을 통과해야 한다. 원문에 존재하지 않는 조항 인용은 해당 finding을 폐기한다(할루시네이션 차단).

- 개인정보는 전달 전 마스킹한다. 마스킹 실패 시 호출 자체를 중단하고 F-A-08 경보를 발생시킨다.

- 모든 AI 결과 화면에는 '참고 정보이며 법률 자문이 아님' 고지와 근거(표준약관·소비자분쟁해결기준 조항)를 병기한다.

- 결정적 계산(위약금·총액·수수료)은 LLM을 사용하지 않고 lib/core/pricing의 순수 함수로 처리한다.

### 5.2 계약서 검토 파이프라인 (F-C-07) — 8단계

| **단계**        | **처리**                                                                          | **구현 위치**                    | **실패 시**                        |
|-----------------|-----------------------------------------------------------------------------------|----------------------------------|------------------------------------|
| 1. 수집        | 카메라·파일 업로드. 20MB 규격, 클라이언트 리사이즈. 파기 정책 동의 확인           | 클라이언트 + POST /api/documents | 동의 없으면 업로드 차단            |
| 2. 텍스트 추출 | PDF 텍스트 레이어 우선, 이미지·스캔본은 OCR                                       | 서버(추출 워커)                  | 품질 미달 시 재촬영 안내           |
| 3. 마스킹      | 이름·연락처·주민번호·주소·계좌·사업자번호 치환. 마스킹 맵은 메모리에서만 유지     | lib/core/masking                 | 미검출 위험 패턴 존재 시 중단·경보 |
| 4. 룰 스캔     | 검출 룰 20종 패턴 매칭(결정적). 후보 조항과 rule_code 산출                        | lib/core/rules                   | 매칭 0건이어도 5단계 진행          |
| 5. LLM 분석    | 마스킹 원문 + 룰 후보 + 근거 조항 컨텍스트로 위험 조항 판정·설명·협상 문구 생성   | Claude API(서버)                 | 재시도 1회 후 실패 처리            |
| 6. 스키마 검증 | ReportSchema(zod) 통과 여부. 등급·근거 필드 필수                                  | lib/core/schemas                 | 재시도 → 실패 시 폐기              |
| 7. 인용 대조   | 각 finding의 clause_excerpt가 원문에 실재하는지 문자열 대조                       | 서버 검증기                      | 불일치 finding 개별 폐기           |
| 8. 저장·파기   | 구조화 결과(findings)만 DB 저장, 원문은 purge_scheduled_at 설정 후 24시간 내 파기 | DB + purge-documents             | 파기 실패 시 F-A-08 경보           |


### 5.3 위약금 시뮬레이터 (F-C-08)

LLM을 사용하지 않는다. penalty_rules(소비자분쟁해결기준 기반)와 계약서에서 추출된 조항을 입력으로 lib/core/pricing/penalty.ts가 결정적으로 계산한다.

- 입력: 카테고리, 총액, 계약금, 예식일, 취소 시점, 계약서 규정 위약률

- 출력: 기준 위약금, 계약서 기준 위약금, 초과분, 근거 조항, 이의 제기 문구

- 경계값(취소 시점 구간 경계, 계약금 반환 여부)은 vitest 단위 테스트 필수 — 05 §3 개발 플로우

#### 플래너 가드레일

- 법률·세무·의료 판단 요청은 일반 정보 제공 + 전문가 상담 안내로 처리하고 확정적 결론을 내리지 않는다.

- 가격·업체 사실 주장은 반드시 툴 조회 결과에 근거해야 하며, 미조회 상태의 수치 생성은 금지한다(프롬프트 제약 + 응답 후처리 검사).

- 무료 사용자 일일 턴 제한, 세션당 토큰 상한, 남용 탐지 시 레이트리밋.

### 5.6 가격 이상 탐지 (F-A-14)

### 7.2 보안

- 전 테이블 RLS 활성화. 서비스롤 키는 Route Handler·Edge Function 전용이며 클라이언트 번들 유입 여부를 CI에서 검사한다.

- 결제 웹훅은 서명 검증 후 처리하고, 멱등 키로 중복 반영을 차단한다.

- 인증은 Supabase Auth 세션 쿠키(HttpOnly, Secure, SameSite=Lax). 운영자 계정은 2단계 인증 필수.

- 민감 식별자(전화번호·사업자번호)는 해시 또는 암호화 컬럼으로 저장하고 평문 조회 API를 만들지 않는다.

- 의존성 취약점 스캔(npm audit)과 시크릿 스캔을 PR 파이프라인에 포함한다.

- admin·vendor의 상태 변경 액션은 예외 없이 audit_logs에 기록한다.

### 7.4 신뢰성 · 운영

- 환경 3단 분리: local(Docker) → staging(Supabase 프로젝트 A + Vercel Preview) → production(프로젝트 B).

- DB 백업: Supabase 자동 백업 + 마이그레이션 기반 재구성 가능성 상시 유지(supabase/migrations 단일 진실).

- 장애 대응: Sentry 알림 → 피처 플래그로 해당 기능 격리 → 롤백. AI 장애 시 도구 화면은 '일시 이용 불가' 상태로 degrade하고 나머지 기능은 유지한다.

- 외부 의존성 실패 처리: Claude API·토스·알림톡 각각 타임아웃·재시도·서킷브레이커 정책을 정의한다.

- 배치 실패는 job_runs에 기록하고 파기 배치 실패는 즉시 경보(개인정보 사고 직결).

### 7.6 앱 (Capacitor)

- 원격 URL 모드 기본, 코어 화면은 정적 내장으로 심사 리스크 완화(05 §1).

- 네이티브 기능 3종: 카메라(@capacitor/camera, 업로드 전 클라이언트 리사이즈 ≤20MB), 푸시(FCM+APNs), 스토어 입점.

- 디지털 멤버십 결제는 스토어 정책 준수(웹 결제 링크아웃). 실물 서비스 예약 결제는 외부 PG 허용 범위로 처리.

- 딥링크: 공유 리포트·커플 초대용 유니버설 링크·앱 링크 설정.

- iOS는 로컬 macOS 부재 전제로 클라우드 CI 빌드·배포(05 §3).

### 7.7 법적 표현 원칙

- AI 검토·진단 결과에는 항상 '참고 정보이며 법률 자문이 아님'을 병기하고 근거 조항(표준약관·소비자분쟁해결기준)을 함께 제시한다.

- 위약금 계산은 '기준 대비 비교값'으로 표현하며 확정적 법적 결론이나 승소 가능성을 언급하지 않는다.

- 업체에 대한 부정적 판단은 사실(등록가·계약 내역)과 기준 대비 편차로만 표현하고, 평가적 단정 표현을 사용하지 않는다.

- 검증 후기는 거래 이력 기반임을 표기하고, 삭제·비공개 처리 기준을 공개한다.
