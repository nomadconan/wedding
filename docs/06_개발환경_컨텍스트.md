### Node 버전 고정 방침 (2026.8 · T-00b)

**Node 20 LTS(v20.20.2)에 고정한다.** nvm-windows로 관리하며 리포에 세 곳으로 못박아 뒀다.

| 위치 | 값 | 역할 |
|---|---|---|
| `.nvmrc` | `20.20.2` | 버전 선언의 단일 진실. CI(`actions/setup-node` 의 `node-version-file`)와 mac/Linux nvm 이 읽는다 |
| `package.json` 의 `engines.node` | `>=20 <21` | 메이저 이탈 차단. Vercel 이 빌드 런타임 선택에 참고한다 |
| (예정) CI 워크플로 `setup-node` | `node-version-file: .nvmrc` | S8-05에서 연결한다 |

> **주의(nvm-windows)** 설치본은 **nvm-windows 1.2.2** 이고, 이 버전은 인자 없는 `nvm use` 로 **`.nvmrc` 를 읽지 못한다**(mac/Linux 용 nvm 과 다른 점). 윈도우에서는 버전을 명시해서 전환한다:
>
> ```bat
> nvm use 20.20.2
> ```
>
> `.nvmrc` 는 그래도 둔다 — CI·Vercel·다른 OS 개발자가 참조하는 **선언적 단일 진실**이기 때문이다. 값을 바꿀 때는 `.nvmrc` 와 `engines` 를 함께 고친다.

**근거**

1. **Next.js 14 지원 범위** — Next 14는 Node 18.17+ 를 요구하며 **검증된 조합은 18·20 LTS**다. 24.x 는 지원 매트릭스 밖이라 문제가 생겨도 프레임워크 쪽 보증이 없다.
2. **Vercel 배포 런타임과 로컬 일치** — Vercel의 Node 런타임 선택지가 LTS 기준이라, 로컬만 24.x 로 앞서가면 **로컬은 되는데 배포는 깨지는** 상황을 만든다. 배포 대상과 같은 메이저를 쓰는 편이 안전하다.
3. **CI 재현성** — `npm ci` 가 로컬·CI·배포에서 같은 결과를 내야 한다. 메이저가 갈리면 네이티브 의존성 재빌드에서 차이가 난다.

**버전을 올릴 때**는 세 곳(`.nvmrc` · `engines` · CI)을 함께 바꾸고, Next 지원 매트릭스와 Vercel 런타임 선택지를 먼저 확인한다.

> **주의(Windows·nvm)** nvm-windows는 `NVM_SYMLINK`(예: `C:\nvm4w\nodejs`)를 PATH에 걸어 버전을 전환한다.
> **버전 전환 후에는 터미널을 새로 열어야** PATH가 반영된다. 이미 떠 있던 셸·에디터·에이전트 프로세스는
> 이전 환경 변수를 그대로 물고 있어 `node` 를 못 찾거나 옛 버전을 가리킬 수 있다.

## 3. 명령 규칙 (Windows CMD 기준)
- 코드·안내에서 명령은 **CMD 문법**으로 제시한다: `copy`(cp 아님), `\` 경로 구분, `%VAR%` 환경변수, `::` 주석. bash 전용 문법(`export`·`$VAR`·heredoc) 사용 금지.
- Supabase CLI는 전역 PATH에 없다. 반드시 `npx supabase ...` 형태로 호출한다.
- 반복 작업은 `scripts\*.bat`으로 스크립트화한다. 배치 파일은 `@echo off` + `call npm ...` 패턴.
- Python 보조 스크립트는 **소스 ASCII-only** 원칙(주석·문자열에 한글 직접 삽입 금지) — Windows CMD 인코딩 사고 방지.
- 파일 인코딩: 소스·문서 UTF-8. 한글 파일명 허용(문서·산출물), 코드 파일명은 영문.

## 5-1. 로컬 계정 셋업 (S0-02)

| `ops@local.test` | `ops` | 운영 담당자. admin과 같은 접근 범위 |

기본 비밀번호는 **`local-dev-1234`** 이며 실행할 때마다 콘솔에 출력된다.
**로컬 전용 값이다.** 리포에 계정 정보를 커밋하지 않고, 다른 환경에서 재사용하지 않는다.

`vendor_applications`(**submitted**) 1건. 승인 전 상태로 두는 이유는 `/admin/vendors` 에서
**실제 승인 플로우를 처음부터 밟아 볼 수 있게** 하기 위해서다. 승인한 뒤 다시 해 보려면
`--reset` 을 쓴다.

> **안전장치** `NEXT_PUBLIC_SUPABASE_URL` 이 `127.0.0.1`·`localhost` 가 아니면 스크립트가
> 즉시 중단한다. 스테이징·프로덕션에 데모 계정을 만들 수 없다.

### 접근 권한이 결정되는 위치

권한 판정이 어디서 일어나는지 알아야 화면이 막힐 때 어디를 볼지 안다.

| 대상 | 1차 | 2차(역할) | 최종 경계 |
|---|---|---|---|
| `/admin/**` | `middleware.ts` — **로그인 여부만** 본다 | 화면: `requireOperator()` → `profiles.role ∈ {ops, admin}` / API: `isOperator()` → 아니면 **403** | **서버 코드**다. 운영자에게는 RLS 정책을 주지 않고 서비스롤 경유로만 접근한다(07 §3.9) |
| `/vendor/**` | `middleware.ts` — 로그인 여부만 | 화면: `requireUser()` + `vendor_members` 소속 조회. 수정 가능 여부는 `vendor_role='owner'` | **RLS**다. `is_vendor_member` / `is_vendor_owner` 가 판정하며 화면 체크는 UX 보조다 |

- **`profiles.role` 은 `/vendor/**` 접근에 쓰이지 않는다.** 업체 화면의 조건은 `vendor_members` 소속이다.
  시드가 `vendor_owner` 역할을 넣는 것은 표기용이며 인가에 관여하지 않는다.
- 미인증은 `/login?next=...` 로, 권한 부족은 `/login?next=...&denied=1` 로 보낸다.

> **플래너 계정은 전용이다**(S6-01). `planner@local.test` — 소비자 계정을 겸하면 "플래너"와 "커플 구성원"이 같은 사람이 되어 위임 격리 검사가 **엉뚱한 이유로 통과**한다. 시드는 플래너 레코드와 **활성 위임**(`couples`·`carts`·`consultations` — 채팅·결제는 닫힌 채)까지 만들고, **카테고리 선택(`planner_scopes`)은 시드하지 않는다** — 그것은 고객의 행위이고 `rls-check` 가 트랜잭션 안에서 만들었다 되돌린다.

> **왜 커플 계정이 네 개인가**(S4-04). `db:rls` 는 이미 존재하는 커플이 필요하고, S0-02 의 온보딩 데모는 `couple-a`·`couple-b` 에 커플이 **없어야** 한다. 같은 쌍으로 둘 다 만족시킬 수 없다. 플래그로 가르는 방법도 있었지만 기억해야 할 모드가 생기고 기본값에서는 한쪽이 깨진 채로 남는다. 계정을 두 개 더 두면 **플래그 없이 둘 다 항상 동작한다** — `couple-a`·`couple-b` 는 그대로 두고 `couple-linked-*` 가 픽스처를 맡는다.

> 연동 커플에는 **커플·멤버·온보딩 답변만** 시드한다. 장바구니·찜·채팅방은 넣지 않는다 — `rls-check` 가 트랜잭션 안에서 만들고 되돌리는 픽스처와 충돌하고(활성 장바구니 부분 유니크, `uq_chat_rooms_couple_vendor`), 영구 데모 데이터가 있으면 빈 상태 화면을 검토할 수 없다.

> 시드 업체는 `pending` 으로 시작한다(승인 플로우 데모). **채팅·상담 예약은 승인된 업체하고만 열린다**(`is_active_vendor`, S4-01) — `/admin/vendors` 에서 승인한 뒤에 `/explore/[vendorId]` 의 '업체에 문의하기' 가 동작한다.

> **증적 기록은 `lib/audit/record.ts` 의 `recordEvent()` 로만 한다**(S4-03). `entity_events` 에 직접 insert 하지 않는다 — `entityType` 이 테이블 이름으로 좁혀져 있고 RLS 열람 정책이 그 전제 위에 서 있다. 원문·개인식별정보를 넣을 자리는 애초에 없다(§7.3).

> **소비자 하단 탭**은 홈·탐색·장바구니·찜·마이 다섯이다(S3-11·S3-09). 다섯이 상한이라 여기서 더 늘리지 않는다. 비교·업체 상세·참가격·**채팅**은 2차 화면이라 각각의 1차 화면에서 들어간다.

> **장바구니는 커플당 하나가 아니다**(S3-12 / IDEA-01). 활성 최대 N개이며 값은 `app_settings.cart.max_active`(초기 5)가 갖고 **판정은 DB 트리거**다 — 생성이 요청마다 하나씩이라 API 카운트는 배우자의 동시 요청을 지나간다. 설정 행이 없으면 **1로 좁힌다**(0016 의 옛 동작). 순번은 **빈 번호를 채우고**, 치우기는 삭제가 아니라 `abandoned` 다(증적이 가리킬 행을 없애지 않는다). 판정은 전부 `lib/core/cart/multi-cart.ts` 한 곳이다.

> **총액만으로 우열을 정하지 않는다**(S3-12). 장바구니끼리 비교에서 담은 카테고리가 다르면 '가장 낮은 총액' 배지를 달지 않는다 — 덜 담은 쪽이 싼 것은 당연하고 그것을 우승으로 적으면 표가 거짓말을 한다. 예산이 미정이면 기준선을 **아예 그리지 않는다**(0원 대비로 말하지 않는다).

> **업체 알림은 두 층이다**(S4-14). 조직이 대상과 채널을 정하고(`vendor_settings`·`vendor_notification_prefs`) 개인이 그 안에서 자기 채널을 끈다(`notification_prefs`) — **둘 다 통과해야 나간다.** 개인 설정만 두면 새 staff 가 들어올 때마다 아무도 못 받고, 조직 설정만 두면 개인이 야간 푸시를 끌 수 없다. `in_app` 은 어느 층에서도 끌 수 없다. 발송 대상 판정은 `lib/vendor/settings.ts` 의 `vendorDelivery()` 한 곳이며 채팅·문의·상담이 같은 함수를 쓴다.

> **영업시간은 SLA 판정에 쓰지 않는다**(S4-14). 쓰면 **업체가 자기 SLA 기준을 자기가 정하는 구조**가 되고, SLA 는 고객 보호 장치다(F-V-15). 대신 셋으로 가른다 — 판정 기준은 벽시계 그대로 / 알림 발송 시각은 영업시간을 존중(다음 영업 시작으로 미룸) / 고객 안내에 영업시간을 적어 기대를 맞춘다.

> **업체 초대 토큰은 커플 초대 코드와 다르다**(S2-09). 커플은 **말로 불러 주는** 8자 코드라 짧고 헷갈리는 글자를 뺐지만, 업체는 **이메일 링크**라 옮겨 적을 일이 없고 권한이 가격·정산에 닿으므로(§3.9) 긴 랜덤 토큰이다. 수락은 **초대받은 이메일로 로그인해야** 되고, 수락 처리만 서비스롤이다(`vendor_members` INSERT 가 owner 전용이라). **미가입자의 발송 증적은 `vendor_invites.sent_at`** 이 갖는다 — `notifications.user_id` 가 `auth.users` FK 라 계정 없이는 행을 만들 수 없다.

> **보증금은 플랫폼의 벌금이 아니다**(S4-07 · D-22 · D-24). 양측이 합의한 조건을 플랫폼이 보관했다가 **§3.11 규칙대로** 집행하는 것이고, 그래서 종결에는 사유가 반드시 붙는다(`consultation_deposits_resolved_chk`). 판정은 `lib/core/consultation` 의 **순수 함수 하나**가 하고 화면·API·배치가 그것을 부른다 — 규칙이 세 곳에 흩어지면 세 곳이 다른 답을 낸다. **양측 무응답의 기본값은 환불**이다: 몰취가 기본이면 업체는 방치가 이득이 되고 확인 절차가 형해화된다.

> **결제 어댑터는 골격이다**(S4-08 · D-28). `lib/payments` 에 인터페이스 + 로컬 스텁이 있고 실연동은 토스 계약 후다. **프로덕션에서 스텁이 돌면 예외로 끊는다** — 알림 스텁은 안 보내고 보냈다고 하는 것이지만, 결제 스텁은 있지도 않은 돈을 두고 몰취 판정이 돌아가게 만든다. 멱등 경계는 `consultation_deposits.idempotency_key` 유니크이며 스텁도 같은 계약을 지킨다.

> **회차 결제는 DB 가 마지막 경계다**(S5-06 · 0030). 승인(`paid`)이 되려면 셋이 동시에 참이어야 한다 — **계약이 확정(active)** · **결제 전 고지·동의 기록 2종** · **상태와 시각의 짝**. 앱에서만 검사하면 결제 경로가 늘 때(재시도 배치·운영 보정) 한 곳만 빠뜨려도 고지 없는 결제가 장부에 남는다. 회차당 **진행 중 1건·성공 1건**이 부분 유니크이고, 종결 상태는 되돌릴 수 없다(D-23). 회차는 결제 실패로 되돌리지 않는다 — `void` 로 만들면 비율 합이 깨진다.

> **결제 멱등은 두 방향이다**(S5-06). 나가는 요청은 **서버가 회차 id 로 만든다**(`paymentIdempotencyKey`) — 클라이언트가 정하면 매 요청이 새 열쇠가 되어 같은 회차가 두 번 결제된다. 들어오는 웹훅은 `(provider, event_id)` 유니크가 판정하며, 순서는 **서명 검증 → 중복 확인 → 상태 전이**다. 서명이 틀린 요청은 **수신 원장에 행을 만들지 않는다** — 만들면 남이 보낸 이벤트 id 로 진짜 이벤트를 막을 수 있다(선점). 서명 비밀이 없으면 **거부한다**(닫힌 쪽으로 실패).

> **결제 실패는 화면 전환이 아니다**(S5-06). 같은 화면의 결과 영역에 **다음 행동과 함께** 적는다. 재시도 상한(`app_settings.payment.max_attempts`)에 닿으면 다른 결제 수단이나 고객센터를 안내한다. API 는 실패를 **402** 로 돌려준다 — 200 으로 내리면 화면이 성공으로 그린다.

> **정산은 결제와 함께 서지 않는다**(S5-06 · O-15). `settlement.fee_basis` 가 미결이면 정산을 세울 수 없지만 **결제를 막지 않는다** — 고객이 낼 금액은 계약 총액이 정하고, 수수료를 할인 전·후 어디서 뗄지는 플랫폼과 업체 사이의 문제다. 대신 보류를 `entity_events`(`settlement_deferred`)로 남겨 **셀 수 있게** 한다. 플래너 수수료(D-17)는 **계약 확정 시점**에 발생한다 — 결제가 아니다. 계약은 서명으로 성사되고 결제는 그 이행이다.

> **위약금 엔진을 두 벌 만들지 않는다**(S5-08). 구간 판정·금액 산정은 T-04 의 `lib/core/pricing/penalty.ts` 하나이고, 해지 태스크는 그 **결과를 환불·잔여 청구로 나누는 일**만 한다. 룰 수치는 `lib/pricing/penalty-rule-set.ts` 가 주입하며 **DB(`penalty_rules`) 우선·코드 가정치 폴백**이다. **가정치 시드를 넣지 않았다** — 법무 검수 전 수치를 DB 에 넣으면 그것이 운영 기준처럼 굳는다(0029 가 조항 문안에서 내린 판단과 같다). 확정되면 **행을 넣기만 하면** 코드 변경 없이 전환되고, 그때까지 `isDraft` 가 화면까지 실려 나간다(§7.7).
>
> **해지에서 귀책은 주장과 확정이 다르다**(S5-08 · D-24). 당사자가 고른 값은 `couple_claim`·`vendor_claim` 이고 `fault` 는 **양측 일치 또는 운영자 조율**로만 정해진다. 나누지 않으면 사유 선택 하나가 곧 정산 결과가 된다. **귀책 미정으로는 정산할 수 없고** DB 트리거가 그것을 막는다. 업체 귀책이면 위약금 없이 전액 환불이지만 **배상액은 코드가 만들지 않는다**(O-03 대기 — 조율 대상).
>
> **무응답을 동의로 읽지 않는다**(S5-08). S4-07 은 상담 보증금에서 "양측 무응답의 기본값은 환불" 로 정했지만, 계약 해지는 **금액이 크고 귀책에 따라 결과가 정반대**라 기본값을 만들 수 없다. 기한이 지나면 `/admin/penalties` 조율 큐로 간다 — 자동 집행보다 사람이 보는 편이 낫다.
>
> **예약 확정이 재고 자리를 잡는다**(S5-08 · S2-05 가 남긴 자리). 계약 확정(`contracts.active`, 서명의 사건)과 예약 확정(`bookings.confirmed`, 자리의 사건)은 **다른 사건**이다. `inventory_slots.remaining` 은 후자에서 줄고 취소에서 되돌아오며 트리거가 판정한다(동시 확정은 `for update` 잠금이 막는다). **자리 없는 계약도 가능**하고(스튜디오·드레스), 자리가 붙어 있는데 남은 자리가 없으면 확정을 막는다. **확정된 예약은 자리를 옮길 수 없다** — 취소 후 다시 예약해야 두 단계가 각각 판정된다.
>
> **환불은 나중 회차부터**(S5-08). 계약금(1회차)이 위약금의 기준이자 마지막까지 남는 돈이고(T-04 `refundDeposit`·검출 룰 R-02), 잔금부터 돌려주면 부분 환불이 회차 경계를 덜 넘는다. **미납 회차를 `void` 로 만들지 않는다** — 0028 의 비율 합 트리거가 커밋을 막고, 계약이 `cancelled` 가 되면 0030 이 이미 결제를 막는다.
>
> **이미 지급된 플래너 수수료를 코드가 회수하지 않는다**(S5-08). `earned`·`payable` 은 `void` 로 무효화하지만 `paid` 는 **회수 대상으로 표시하고 조율로 넘긴다** — 계좌로 나간 돈을 자동으로 되가져올 방법이 없고 상계할 다음 지급이 있을지도 코드가 알 수 없다.
>
> **미결정으로 막힌 정산은 '실패' 가 아니라 '설정 대기' 다**(S5-07 · O-15). `settlement.fee_basis` 가 비면 정산서를 `blocked` + `blocked_reason` 으로 남기고 화면은 **설정 대기**로 적는다 — '실패' 로 그리면 업체는 장애로 이해해 문의하고 운영은 없는 장애를 코드에서 찾는다. **거래 내역은 이미 모여 있고** 기준만 채우면 **같은 행이 재계산**된다(새 행을 만들지 않는다 — 증적이 가리키던 id 가 바뀐다). 기준은 계산이 선 시점에 **스냅샷으로 박힌다**(D-16 과 같은 이유).
>
> **확정된 정산서는 고치지 않고 상계로 넘긴다**(S5-07 · D-23). 동결 트리거가 금액 변경을 막고, 조정은 `settlement_adjustments` 에 쌓여 **다음 정산이 가져간다**. 상계는 **건 단위로 들어가거나 통째로 이월**되며(쪼개면 한 건이 두 정산서에 걸려 재현이 어렵다) **지급액은 음수가 되지 않는다**. `settlement_items.adjustment`(0003)와 다른 층이다 — 그쪽은 건별, 이쪽은 **기간을 건너뛰는** 조정이다.
>
> **정산 지급도 어댑터 + 스텁이다**(S5-07 · D-28). 결제 스텁과 같은 이유이고 방향만 반대다 — 결제 스텁이 돌면 받지 않은 돈을 받았다고 적히고, **지급 스텁이 돌면 보내지 않은 돈을 보냈다고 적힌다.** 업체는 '지급 완료' 를 보고 오지 않는 입금을 기다리며, **우리 장부는 정상으로 보인다.** 프로덕션 기본값은 `noop`(실패를 돌려준다)이고 `PAYOUT_ADAPTER=stub` 은 예외로 끊는다. 멱등 열쇠는 `settlement:<id>:payout:<attempt>` 이며 **자동 재시도에서 회차를 올리지 않는다**.
>
> **정산 금액은 업체가 쓸 수 없다**(S5-07 · §3.9). 열람은 **대표 전용**(0028 이 staff 를 DB 에서 막았다)이고, 쓰기는 **이의 제기 메모(`vendor_note`) 하나뿐**이다 — 그것도 정책이 아니라 **컬럼 권한**으로 좁혔다. 정책은 행을 가르고 컬럼을 가르지 않으므로 이의 제기 정책만 두면 금액까지 열린다.
>
> **세금계산서는 자료까지다**(S5-07 · F-V-09). 발행에는 국세청 연동 또는 대행사 계약(D-28)과 **사업자 정보 평문**이 필요한데 후자를 우리가 갖고 있지 않다(§7.2 — `biz_no_enc` 는 해시). 그 상태에서 발행을 흉내 내면 **세금계산서처럼 보이는 문서**가 생기고 회계에서 실제로 쓰인다. 과세 대상은 **정산액이 아니라 중개 수수료**다 — 거래 대금은 고객과 업체 사이의 것이고 플랫폼이 제공한 용역의 대가는 수수료뿐이다(D-24).
>
> **리뷰 대가 쿠폰은 스키마가 막는다**(S5-11 · §7.7 · D-03). `coupons.issue_condition` 을 자유 텍스트로 두면 "후기 작성 시 5천원" 이 언제든 들어온다 — 허용 값 집합을 CHECK 로 제한하고 리뷰·후기·평점 관련 값을 **집합에 넣지 않는다.** `db:rls` 가 코드 목록과 DB CHECK **양쪽**을 본다. 정률 쿠폰에는 **상한이 필수**이고(상한 없는 정률은 업체 정산을 통째로 지운다) 만료일은 **발급 시점 스냅샷**이다(D-16). 부담 주체(`borne_by`)도 사용 시점에 박아 과거 정산이 소급 변경되지 않게 한다.
>
> **정책끼리 서로를 조회하면 무한 재귀다**(S5-11). `coupons` 정책이 `coupon_issues` 를 보고 그쪽이 다시 `coupons` 를 보면 Postgres 가 그 자리에서 멈춘다(`infinite recursion detected in policy`). 0016·0028 이 쓴 방법대로 **조인을 `security definer` 함수로 감싸** 고리를 끊는다 — 새 표에 교차 참조 정책을 쓸 때 먼저 이 함정을 확인한다.
>
> **요율이 하나도 없으면 거래가 서지 않는다**(S5-03 · F-A-15). `commission_rates` 가 0행이면 계약 발행이 `CONTRACT_RATE_UNRESOLVED` 로 막히고 결제·정산·해지가 전부 따라 막힌다. 명세 §부록이 F-A-15 를 **"개발 블로커 해제 장치"** 라고 적은 이유이며, **로컬 데모 요율은 `seed-accounts.mjs` 가 만든다** — 값이 미확정(O-02)이라 마이그레이션에 넣지 않았다(0031 이 위약금 가정치에서 내린 판단과 같다). 운영 값은 `/admin/commission-rates` 에서 넣는다.
>
> **요율 이력은 지우지 않는다**(S5-03 · D-23). 과거 계약의 요율은 스냅샷으로 박혀 있지만(D-16) **그 스냅샷이 어디서 나왔는지**를 답하는 것은 요율 표다. 그래서 변경은 **새 행**, 종료는 **`effective_to` 를 닫는 것**이고, 0034 가 두 표의 **INSERT·UPDATE·DELETE 권한을 회수**했다 — API 에도 DELETE 라우트가 없다. 쓰기는 서비스롤 경유이고 **열람만 정책으로** 연다(§5.5).
>
> **요율 해석은 한 곳이다**(S5-02). 관리 화면의 시뮬레이터도 `resolveRate` 를 그대로 부른다 — 화면용 계산을 따로 만들면 언젠가 시뮬레이터와 실제 계약이 다른 요율을 말한다. 겹침은 0006 의 EXCLUDE 가 최종 경계지만 **저장 전에 어느 행과 부딪혔는지**를 먼저 알려준다.
>
> **에스크로 예치 대상은 잔금이다**(S5-09 · F-C-16). 계약금(1회차)은 계약 성립의 증표이자 위약금의 기준이라(T-04 · 검출 룰 R-02) 묶지 않는다 — 묶으면 **계약이 성립해도 업체는 아무것도 받지 못한 채** 예식일까지 준비 비용을 먼저 쓴다. 회차가 늘어도 규칙은 "첫 회차를 뺀 나머지" 다.
>
> **에스크로의 무응답 폴백은 S4-07 과 반대다**(S5-09). 보증금은 "몰취가 기본이면 업체의 방치가 이득" 이라 환불을 기본으로 뒀지만, 에스크로는 **환불이 기본이면 고객의 방치가 이득**이 된다 — 서비스는 이미 이행됐는데 확인만 안 하면 업체가 영원히 돈을 못 받는다. 그래서 **기본값은 릴리즈**이고, 다만 **예식일 경과를 조건으로** 넣는다(예식 전에는 이행이 없었다). 한쪽이라도 "이행되지 않았다" 고 하면 **즉시 조율**이라 자동 릴리즈가 그것을 덮지 않는다.
>
> **양측 확인 판정은 공통이고 해석은 도메인이 한다**(S5-09). `lib/core/confirmation/two-sided.ts` 가 `대기/일치/불일치/기한경과` 까지 판정하고, **기한 경과의 뜻**은 호출부가 정한다 — S4-07 환불 · S5-08 조율 · S5-09 릴리즈. S4-07 은 불리언이 아니라 4값 outcome 대조라 **옮기지 않았다.**
>
> **에스크로 실예치는 두 층을 지나야 한다**(S5-09 · D-28 · O-03). `app_settings.escrow.enabled`(전자금융업 등록 등 **O-03 대기라 false**)와 어댑터(프로덕션에서 스텁 거부). 둘 다 통과해야 돈이 움직이고 그 전까지는 절차·기록이 돈다. **어댑터는 PG 사 위탁을 수용하는 모양**이다 — 자금 보관은 요건이 무거워 직접 보관보다 위탁이 현실적일 수 있고, 인터페이스는 "우리가 계좌에 넣어 둔다" 를 전제하지 않는다.
>
> **보관 중인 돈은 정산에 들어가지 않는다**(S5-09 → S5-07). 완납과 이행 확인은 다른 사건이다 — 잔금을 냈다는 것과 서비스가 이행됐다는 것은 별개다. 열린 홀드가 있으면 그 예약은 **이번 기간에서 빠지고 다음 기간에 다시 후보**가 된다.
>
> **플래너는 축이 둘이다**(S6-01 · D-43 초안). `planner_engagements`(0004)는 **열람 권한 위임**(표 단위 · RLS 의 `has_planner_scope` 가 판정)이고 `planner_scopes`(0036)는 **카테고리별 이용 여부**(과금)다. 합치면 "예산은 보게 하되 어느 카테고리에도 플래너를 쓰지 않는다"(상담만 받는 단계)를 표현할 수 없다. **한쪽을 끄면 다른 쪽도 꺼진다고 가정하지 않는다** — 카테고리를 빼도 위임은 살아 있으므로 화면이 두 경로를 함께 안내한다.
>
> **플래너 카테고리 선택은 삭제하지 않는다**(S6-01 · D-23). "언제부터 언제까지 이 카테고리에 플래너를 썼는가" 가 정산 분쟁의 질문이라 해제는 `status='released'` + `released_at` 이고 **재선택은 새 행**이다(동시 선택 1건은 부분 유니크). **요율은 여기 없다** — `planner_fee_rates` 가 갖고 계약 확정 시 스냅샷된다(D-16). **활성 위임이 있는 플래너만** 카테고리에 지정할 수 있다(트리거) — 없으면 보지도 못하는 플래너에게 수수료가 붙는다.
>
> **카테고리 선택은 커플 구성원 누구나 한다**(S6-01). 결제·계약 서명이 owner 전용인 것과 다른 층 — 이것은 **구성 선택**이지 돈을 움직이는 확정이 아니고(과금은 계약 확정 시 스냅샷) 장바구니 항목 토글을 배우자도 바꿀 수 있는 것과 같다. **플래너는 읽기만** 한다 — 스스로 범위를 넓히면 자기 수수료를 늘리는 행위다.
>
> **플래너 랭킹은 지금 지표 하나만 셀 수 있다**(S6-01 · D-25 · O-13). 계약 건수(`planner_settlements`)뿐이고 상담(S6-04)·예약(S6-03)·리뷰(S8-11 — `reviews` 는 업체 대상이라 플래너 후기 구조가 없다)·프로필 방문(S8-10)은 **0이 아니라 "아직 세지 않는다"** 로 표시한다. **가중치를 지어내지 않았다** — 종합 점수를 만들면 플래너의 수입이 우리가 지어낸 계수에 좌우된다. **신규 플래너 콜드스타트**(실적 0이 영원히 하위 → 진입 장벽)도 O-13 에 함께 적어야 한다.
>
> **상담 슬롯 중복은 EXCLUDE 로 막는다**(0025). 예약은 시각 하나가 아니라 **구간**을 차지하므로 UNIQUE 로는 14:00·14:30 겹침을 못 잡는다. 자리를 차지하는 상태는 `approved`·`confirmed` 뿐이고 `requested` 는 아니다 — 업체가 후보를 여럿 받아 고르는 흐름을 막지 않기 위해서다. 판정이 **승인 시점에 DB 에서** 일어나므로 동시 승인에서도 하나만 통과한다.

> **견적은 플랫폼 폼으로만 오간다**(S4-12). 견적 항목은 `products`·`product_options` **참조로만** 존재하고(CHECK), 이름·분류·옵션 상한은 **트리거가 등록된 행에서 덮어쓴다** — 항목 자리에 자유 텍스트를 넣을 방법이 없다. 금액은 `price_rules` 평가 결과를 상한으로 삼아 **할인만** 되고 할증은 CHECK 가 막는다. 상한 계산이 `lib/core/pricing` 의 순수 함수라 DB 가 스스로 검증할 수 없어 **`quotes`·`quote_items` 쓰기 권한을 회수하고 서버(서비스롤) 경유로 좁혔다**. 견적에 **첨부 컬럼을 두지 않는다** — 파일로 보내는 순간 플랫폼 밖 양식이 되고 위 장치가 전부 무의미해진다.

> **업체에 말을 거는 길이 셋이고 결과물이 다르다** — 문의·견적(`/inquiries`)은 견적서를, 채팅(`/chat`)은 합의를, 문의게시판(`/qna/[vendorId]`)은 공개 지식을 남긴다. 문구는 `lib/core/inquiry/inquiry.ts` 의 `CONTACT_PATHS` 가 갖고 `ContactPathGuide` 가 문의함·업체 상세에 같은 문장을 보여준다.

> **실시간은 Supabase Realtime 이다**(S4-04 · O-11 · D-29 초안). publication 에 들어 있는 표는 **`chat_rooms` 하나뿐**이다 — `chat_messages` 를 구독하면 본문이 소켓을 타고 회수 가림막(`chat_messages_visible`)을 우회한다. 규칙은 **소켓은 신호, 진실은 재조회**이며 구독 훅은 `hooks/use-room-signal.ts` 다. 새 표를 실시간으로 열 때 같은 판단(본문이 payload 에 실리는가)을 먼저 한다.

> **채팅 첨부는 서버를 지나가지 않는다.** 서버는 서명 업로드 URL 만 발급하고 클라이언트가 Storage 로 직접 올린다(§5.3 — 원문이 로그·트레이스에 실릴 자리를 만들지 않는다). 내려받기 주소는 볼 때마다 새로 발급하며 **DB 에 저장하지 않는다**(만료되고, 저장하면 접근권이 샌다).

> **규칙** 화면·API 라우트를 추가하는 태스크는 **완료 시 이 표를 갱신한다.**
> 표에 없으면 확인할 방법을 모르는 화면이고, 그러면 만들어 두고도 아무도 안 본다.
> 기능 ↔ 태스크 대응은 `docs/TASKS.md` 커버리지 검증표가 별도로 관리한다.

## 8. 일상 개발 사이클
1. `dev`에서 기능 브랜치 생성 → 작업. 브랜치명 규약: **`feat|fix|chore|docs/<태스크ID>-<요약>`**
   - 예: `feat/T-05-vendor-onboarding`, `chore/T-02c-asset-convention`, `docs/T-00-spec-v2`
2. DB 변경 시: 마이그레이션 SQL 작성 → `npm run db:reset` 으로 검증 → 커밋 → `npm run db:types`.
3. 커밋 전: `npm run lint && npm run test`.
4. PR → dev 병합 → main 배포. **main 직접 push는 GitHub ruleset(main-protection)으로 차단됨.**
5. 새 의사결정 발생 시 04_의사결정로그.md에 D-번호로 추가(리포 외부 문서).
